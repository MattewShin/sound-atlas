## 사용자 흐름

하단 ‘내 음악 기록’에서 피드를 읽고 Google 로그인 후 직접 공개 닉네임·고유 @아이디를 만든다. Google 실명·이메일·이미지를 프로필로 복사하지 않는다. 구현 시작 커밋에는 실제 인증·음악 기록·공개 프로필 모델이 없었다. 기존 `isLoggedIn` prop은 홈 탐색 회귀 호환용이며 새 기록 권한은 Supabase Auth가 발급한 사용자 JWT만 사용한다.

‘개인 원본’ → ‘새 음악 기록’에서 앱에 등록된 곡 하나와 본문을 선택한다. 기본 ‘나만 보기’는 개인 원본만 만든다. ‘모든 사람’ 또는 ‘내 팔로워’는 공유 범위를 확인·확정한 후 개인 원본과 독립 공유본을 한 트랜잭션에서 만든다. 원본을 먼저 저장한 후 ‘공유본 만들기’로 별도 공유할 수도 있다. 이때도 기본값은 나만 보기다. 기존 보관함·평가·추천 데이터는 이전하거나 공개하지 않는다.

원본 수정은 원본만 바꾼다. 공유본 메뉴의 수정/범위 변경은 공유본만 바꾼다. ‘공유 취소’는 공유본과 그 댓글·좋아요를 삭제하고 원본을 보존한다. ‘개인 원본 삭제’는 기존 공유본을 보존하며 원본 참조만 NULL로 만든다. 범위를 나만 보기로 바꿀 때 댓글·좋아요는 보존한다.

피드에서 프로필·곡 이름을 누르면 각각 프로필·곡별 목록으로 이동한다. 작성 시각을 누르면 정확한 KST 시각을 펼친다. 긴 본문은 더 보기, 줄바꿈은 보존한다. 게시물 메뉴의 링크 복사는 범위를 바꾸지 않는다.

게시물·댓글·좋아요의 직접 REST 요청과 RPC 모두 RLS를 거친다. `social_can_read`는 호출자의 `auth.uid()`만 사용하고, 작성자·공개 범위·현재 팔로우·양방향 차단을 확인한다. `social_feed`와 `social_profile`은 SECURITY INVOKER로 RLS를 적용한 목록·개수를 반환한다. 공개 게시물은 비로그인 조회 가능하고 쓰기는 로그인+공개 프로필이 필요하다. 개인 원본을 공개 피드에서 조회하지 않는다.

차단한 두 사용자는 서로의 프로필·게시물·좋아요·댓글을 조회할 수 없고 팔로우·댓글·반응도 할 수 없다. 차단 시 양쪽 기존 팔로우를 삭제하며 해제해도 자동 복원하지 않는다. 제삼자의 조회는 그 방문자와 각 작성자의 권한을 따른다. 기존 댓글/반응 자체는 삭제하지 않는다. 팔로우를 취소하면 해당 작성자의 팔로워 범위 권한을 잃는다. 열람 권한을 잃은 게시물의 자기 댓글도 다시 접근할 수 있을 때까지 삭제할 수 없다.

| 범위/변경 | 글·댓글·좋아요 목록·개수 | 작성/반응 |
| --- | --- | --- |
| 나만 보기 | 작성자만 조회 | 작성자만 가능 |

| 내 팔로워 | 작성자와 현재 팔로워만 조회 | 같은 열람 권한과 로그인/프로필 필요 |
| 팔로우 취소 | 해당 작성자의 팔로워 범위만 즉시 권한 상실. 공개 글은 계속 열람 | 숨겨진 글의 좋아요 취소·자기 댓글 삭제도 불가 |

차단은 로그인 계정 관계에 적용한다. 로그아웃하면 계정을 식별할 수 없으므로 누구에게나 공개된 글은 익명으로 읽을 수 있다. 제삼자에게 보이는 기존 댓글/좋아요는 그대로 남아 차단한 방문자의 개수와 다를 수 있다.

## 삭제와 데이터 보존

아래는 새 SNS 테이블의 FK/RLS 기준이다. 계정 삭제는 신뢰된 서버/관리자가 `auth.users` 행을 삭제했을 때의 동작이며 이 Draft에 새 계정 삭제 UI/RPC는 없다. 최신 main의 기존 계정 삭제 흐름과 결합 검증은 남아 있다.

| 동작 | 개인 원본/공유본 | 댓글·좋아요·관계·신고 |
| --- | --- | --- |
| 로그아웃/계정 전환 | DB 행 유지, 메모리 화면·진행 요청 폐기 | DB 반응 유지, 이전 계정 초안·화면 재사용 안 함 |
| 개인 원본 삭제 | `music_records`만 삭제. 공유본 내용·범위 유지, `source_record_id`만 NULL | 공유본 댓글/좋아요 유지 |
| 공유 취소/공유본 삭제 | `music_posts` 삭제. 개인 원본 유지 | 그 게시물의 모든 댓글/좋아요는 CASCADE 삭제. 신고 행/스냅샷은 남고 `post_id`만 NULL |
| 본인 댓글 삭제 | 게시물/원본 유지 | 그 댓글만 삭제. 좋아요 유지, 서버 댓글 수 재조회 |
| 나만 보기 전환/팔로우 취소/차단 | 행 유지, RLS로 접근 제한 | 기존 댓글/좋아요 삭제 안 함. 차단 시에만 두 방향 팔로우 삭제 |
| `auth.users` 계정 삭제 | 해당 계정의 `social_profiles`, 개인 원본, 공유본 CASCADE 삭제 | 자기 글에 달린 모든 사람의 댓글/좋아요와, 다른 글에 자신이 남긴 댓글/좋아요 삭제. 자기 계정이 포함된 팔로우/차단 관계도 삭제 |

계정 삭제 시 신고의 `reporter_id`는 NULL이 된다. `reported_author_id`는 FK가 없는 UUID이고 신고 본문 스냅샷·사유와 함께 운영자 전용 테이블에 남는다. 현재 보관 기한/익명화 배치는 없다. 계정 삭제 후 이 운영 기록을 어떻게 보관할지는 배포 전 정책 검토가 필요하다. 이 사실을 ‘모든 데이터 완전 삭제’로 표현하지 않는다.

좋아요는 `(post_id,user_id)` 기본키와 `social_set_like(post, desired)`의 명시적 상태로 중복·재요청에 대응한다. UI는 요청 중 중복 실행을 막고 서버 개수를 다시 읽는다. 댓글은 초안마다 UUID를 만들고 재요청 시 동일 ID로 중복 저장을 방지한다. 전송 실패 초안은 메모리에 보존하고, 해당 게시물 권한을 잃거나 계정 전환 시 제거한다. 원본+공유 생성도 고정 UUID를 이용해 재시도에 멱등적으로 동작한다.

JWT와 사용자별 기록은 메모리에만 둔다. 브라우저의 sessionStorage에는 OAuth 리다이렉트를 잇는 일회용 PKCE verifier만 둔다. 새로고침 후에는 다시 로그인한다. SDK 인증 저장 키는 런타임별로 분리하여 탭 사이에서 UI 계정과 API 토큰이 어긋나지 않게 한다. 탭 간 로그아웃 메시지에는 세션 정보를 넣지 않는다. 로그인 종료·계정 전환 시 화면을 새로 마운트하고 이전 비동기 응답을 무효화한다.

REST fetch는 `cache: no-store`를 사용한다. 피드/댓글/원본은 localStorage·sessionStorage·IndexedDB·서비스워커·공연 검색 캐시에 저장하지 않는다. 추천 계산은 기존 보관곡·감정 점수만 사용한다.

## 실시간 권한 변경

게시물·관계·댓글·반응 변경 트리거는 공개 `atlas-social` 채널에 `invalidate` 이벤트와 빈 `{}`만 보낸다. 사용자 ID·곡 ID·범위·본문을 보내지 않는다. 클라이언트는 즉시 현재 목록을 지우고 RLS로 다시 조회한다. 연결 끊김·오프라인·탭 숨김·페이지 이탈 시에도 목록을 비우고 복귀 후 재검증한다. 연결이 확인되지 않으면 피드를 표시하지 않는다. 요청 세대 번호로 변경 전 응답이 다시 나타나는 것을 막는다. 60초 간격 재조회도 수행한다.

DB는 범위 변경·팔로우 취소·차단 커밋 후 새 요청부터 즉시 거부한다. 이미 수신한 화면 제거에는 네트워크 이벤트 전달 시간이 필요하다. 운영 Realtime의 실제 전송·재연결 지연은 로컬 PGlite/DOM 검증만으로 보장하지 않는다.

## 운영 적용 순서 (아직 미실행)

전제: 위의 최신 main 통합·호환성 문제가 해결되어야 한다. 이번 게시 단계에서는 아래 절차를 실행하지 않는다.

1. 현재 스키마와 적용 이력을 읽기 전용으로 확인하고 스키마/데이터 백업을 확보한 뒤 Supabase 개발/스테이징에서 아래 두 migration을 순서대로 적용한다. `auth.users`, `auth.uid()`, `anon`/`authenticated`/`service_role`이 전제다. 공연/OCR의 기존 미적용 작업과 섞지 말고 대상 SQL을 확인한다.
   - [202611060001_music_social.sql](../supabase/migrations/202611060001_music_social.sql): 테이블·RLS·RPC·트리거
   - [202611060002_social_track_catalog.sql](../supabase/migrations/202611060002_social_track_catalog.sql): 현재 등록 곡 ID/표시 제목. 개인 데이터 없음
2. Supabase Auth에서 Google 공급자를 설정하고 배포 origin과 개발 origin을 허용 리다이렉트 URL에 등록한다. 프런트에 Google 비밀키를 넣지 않는다.
3. Supabase Realtime의 Broadcast from Database가 활성화되어 있고 `realtime.send(jsonb,text,text,boolean)`가 존재하는지 확인한다. `atlas-social` 공개 Broadcast 채널을 허용한다. 콘텐츠 테이블을 Postgres Changes에 공개 복제할 필요가 없다. 실제 두 브라우저로 빈 무효화 이벤트 수신을 확인한다. 함수가 없는 격리 PostgreSQL에서는 트리거가 무효화 이벤트를 보내지 않는다.
4. 프런트 빌드 환경에 `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`(공개 anon/publishable 키)를 넣고 재빌드·배포한다. 서버 `SUPABASE_SERVICE_ROLE_KEY`는 이 변수에 넣지 않는다. 연결 설정이 없으면 준비 중 화면을 표시한다.
5. 스테이징 전용 A/B/C 계정으로 세 공개 범위, 직접 URL/REST, 팔로우·취소·양방향 차단, 로그아웃·새로고침·계정 전환, 네트워크 단절/복구를 검증한다. 실제 개인 원본을 공개하는 방식으로 시험하지 않는다.

001은 신규 9개 테이블·인덱스·함수·RLS·트리거·권한을 한 트랜잭션으로 만든다. 기존 공연/OCR, 로컬 보관/평가, 최신 main의 기록/닉네임/공유본을 변경하는 DML이 없다. 002는 공개 음악 카탈로그 291개 ID의 제목/작곡가를 `social_tracks`에 INSERT/ON CONFLICT UPDATE한다. 사용자/개인 기록 입력은 없다. 기존 기록 자동 공개나 기존 공유 범위 변환은 수행하지 않는다. 이후 곡 추가 때 동일 기존 ID로 migration을 추가하며 ID를 재발급하지 않는다.

신고는 신뢰된 운영 DB 연결 또는 Supabase SQL Editor에서 아래처럼 확인한다. 서비스 키는 운영자 서버에서만 사용하며 브라우저 운영 화면에 넣지 않는다.

```sql
select id, created_at, reporter_id, reported_author_id, post_id, reason, snapshot
from public.social_reports where resolved_at is null order by created_at;
-- 처리한 신고만 운영자가 지정해서 완료 표시한다.
-- update public.social_reports set resolved_at=now() where id='<신고 UUID>';
```

## 적용 실패 시 복구 절차 (문서, 미실행)

1. **001이 COMMIT 전 실패:** 중단된 연결에 트랜잭션이 남았다면 `ROLLBACK`하고 카탈로그에서 테이블/함수 존재 여부를 확인한다. 001 전체가 롤백되었는지 확인한 후 원인을 수정해 재시도한다. `CREATE TABLE/FUNCTION`이므로 이미 적용된 001을 그대로 다시 실행하지 않는다.
2. **001 성공 후 002 실패:** SNS 기능을 비활성 상태로 유지한다. 기존 기록/공연 테이블은 그대로 둔다. 002는 단일 INSERT 문이므로 부분 행만 반영되지 않으며, 원인 수정 후 002만 재시도한다. ON CONFLICT는 새 카탈로그 제목/작곡가만 갱신한다. 전체 미적용 migration 일괄 실행으로 복구하지 않는다.
3. **프런트 연결/배포 실패:** 이전 검증된 프런트 산출물로 되돌리거나 SNS용 공개 URL/키 구성을 제거해 준비 중 상태로 되돌린다. DB의 신규 데이터와 RLS는 보존한다. Git을 이용하면 SNS 기능 커밋을 별도 revert하는 방식으로 검토하며 다른 작업자의 변경을 reset하지 않는다.
4. **권한 오류/정보 노출 의심:** 프런트 되돌리기만으로 직접 API를 막을 수 없다. 신뢰된 운영 DB 연결에서 새 SNS 테이블의 `anon`/`authenticated` 접근과 신규 RPC 실행 권한을 제한하고 빈 Realtime 무효화 신호를 발행해 열린 화면도 재조회하게 한다. RLS를 끄거나 private/followers를 public으로 변경하지 않는다. 원인 수정 후 승인된 migration의 정확한 RLS/GRANT만 복원하고 격리 A/B/C/익명 검증을 통과한 뒤 다시 연다. 기존 main 테이블은 별도 정책을 따르므로 함께 진단해야 한다.
5. **이미 사용자 행이 생긴 뒤:** 테이블 DROP/광역 CASCADE를 기본 복구로 사용하지 않는다. 백업·행 수·FK·적용 이력을 보존하고 데이터 보존형 후속 migration으로 수정한다. 이 PR에는 파괴적인 자동 down migration이 없다. 문서의 복구 절차는 실제 장애 환경에서 실행해 검증한 결과가 아니다.
