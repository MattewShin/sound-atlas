# 웹 GPT와 Codex 공동 작업 안내

이 방식은 GitHub에 저장한 문서를 양쪽이 읽고 갱신하는 방식이다. 문서 수정만으로 다른 AI가 자동 실행되거나 전체 대화가 동기화되지는 않는다.

## 파일별 역할

| 파일 | 역할 | 주 갱신자 |
| --- | --- | --- |
| [AGENTS.md](../AGENTS.md) | Codex가 따를 작업 규칙 | 양쪽, 사용자 지시 반영 |
| [PROJECT_CONTEXT.md](../PROJECT_CONTEXT.md) | 서비스 목적·구조·확정 정책 | 양쪽, 근거와 확인 시점 기재 |
| [CURRENT_TASK.md](../CURRENT_TASK.md) | 현재 요구사항·완료 기준·상태 | 웹 GPT가 명세, Codex가 진행 상태 |
| [HANDOFF.md](../HANDOFF.md) | 구현 결과·의견·질문·검토 답변 | Codex 구현 영역 / 웹 GPT 검토 영역 |

처음 읽을 때는 이 5개 파일을 사용한다. 도메인 세부 사항은 기존 docs 문서를 참조하고 중복 복사하지 않는다.

## 매 작업의 흐름

1. Theo가 웹 GPT에 원하는 결과를 설명한다.
2. 웹 GPT가 GitHub의 최신 CURRENT_TASK·HANDOFF와 관련 코드를 같은 기준 커밋에서 읽는다.
3. 기존 작업을 보관한 후 새 작업 ID·명세 버전·범위·완료 기준을 작성하고 READY로 저장한다.
4. Theo가 Codex에 “공동 문서 기준으로 현재 작업을 진행해줘”라고 요청한다.
5. Codex가 변경을 보존하며 문서를 읽고 구현한다. 진행 상태는 IN_PROGRESS로 표시한다.
6. Codex가 결과·테스트·질문·의견을 HANDOFF에 기록하고 IMPLEMENTED로 저장·공유한다.
7. Theo가 웹 GPT에 “최신 HANDOFF를 검토해줘”라고 요청한다.
8. 웹 GPT가 보고된 브랜치·코드 SHA를 직접 확인하고 ACCEPTED 또는 CHANGES_REQUESTED로 답변을 저장한다.
9. 수정 요청이 있으면 Codex가 같은 작업 ID의 최신 명세로 수정하고 다시 인계한다.

검토만으로 충분한 요청에 새 작업 명세를 만들 필요는 없다. 설명·기획만 원하는지 실제 코드 변경까지 맡긴 것인지 현재 사용자 지시로 판단한다.

## 상태

| 상태 | 의미 | 다음 동작 |
| --- | --- | --- |
| READY | 명세 준비 완료 | Codex가 작업 시작 |
| IN_PROGRESS | 구현 또는 확인 중 | 결과와 주요 중단 지점 기록 |
| BLOCKED | 필요한 정보나 접근이 부족함 | 원인 기록, 독립 작업은 계속 |
| IMPLEMENTED | 구현자가 결과를 보고함 | 웹 GPT가 검토 |
| CHANGES_REQUESTED | 검토 후 수정 필요 | Codex가 수정 |
| ACCEPTED | 명시한 범위의 검토 완료 | 다음 작업 준비 |

CURRENT_TASK와 HANDOFF의 작업 ID·명세 버전·상태를 함께 맞춘다. 문서의 ACCEPTED는 배포 완료를 뜻하지 않는다. 배포·DB 적용 여부는 따로 기록한다.

## 첫 시작

아래는 최초 도입 당시의 예시다. CA-COLLAB-20261022-001은 종료되어 보관되었다. 새 작업에서는 전달받은 작업 브랜치의 최신 CURRENT_TASK를 우선 읽고 실제 작업 ID를 사용한다.

> 원격 main에 추가된 AGENTS.md, PROJECT_CONTEXT.md, CURRENT_TASK.md, HANDOFF.md, docs/AI_COLLABORATION.md를 확인하고 현재 작업 CA-COLLAB-20261022-001을 진행해줘. 먼저 로컬 브랜치와 커밋 전 변경을 확인하고 기존 작업을 보존해줘. 완료 후 HANDOFF의 구현 결과와 의견을 채우고 공유 가능한 브랜치에 반영해줘. 이미 맡긴 개발 작업이 있다면 그 상태도 함께 인계해줘.

Codex가 변경 중인 브랜치에서 일하고 있으면 원격 문서만 별도로 읽거나 안전하게 통합한다. 단순히 최신 문서를 읽기 위해 로컬 변경을 버리지 않는다. 기존 세션에서는 AGENTS.md를 명시적으로 읽게 해 새 규칙을 적용한다.

## 브랜치와 기준 커밋

- 명세는 별도 지정이 없으면 원격 main에서 읽는다. 다른 브랜치에 명세가 있으면 사용자에게 그 브랜치 링크를 제시한다.
- 구현 결과가 작업 브랜치에 있으면 HANDOFF에 그 브랜치와 코드 기준 전체 SHA를 적는다.
- 웹 GPT는 main만 보고 작업 브랜치의 구현을 검토했다고 말하지 않는다. 구현 브랜치의 HANDOFF와 실제 변경을 함께 읽는다.
- 이후 웹 GPT의 검토도 해당 작업 브랜치에 기록하거나 PR에 연결하고 저장 위치를 사용자에게 알려준다.
- 문서의 근거 코드는 고정된 SHA로 확인한다. 문서 저장 커밋 자신을 본문에 넣기 위한 재귀 커밋은 만들지 않는다. 저장 커밋은 GitHub 이력/링크로 확인한다.
- 작업 브랜치가 갱신되어 검토한 SHA와 달라졌다면 새 변경 범위를 먼저 확인한다.

원격 main이 변한 상태에서 옛 내용으로 덮어쓰지 않는다. API 작업은 기대한 HEAD를 확인하는 갱신 방식을 쓰고, 로컬에서는 diff와 원격 변경을 확인한다. 공유 문서 충돌은 양쪽의 구현 기록과 검토 의견을 보존해 해결한다.

## 의견을 주고받는 방법

Codex는 HANDOFF의 구현자 의견과 질문에 문제·근거·권장안·영향을 기록한다. 웹 GPT는 같은 ID에 답변한다. 질문 예:

- Q-001: 기존 확정 결과의 중복 판별 기준이 두 경로에서 다름. 관련 코드와 권장 기준 제시.
- Q-002: 테스트는 통과했지만 실제 로컬 예약 상태는 원격에서 확인할 수 없음. 필요한 확인 항목 제시.

제안은 확정 요구사항과 구분한다. 통상적인 구현 판단은 Codex가 수행하고, 사용자 취향이나 서비스 정책의 미정 사항은 영향과 선택지를 기록한다.

## 기록 보관과 명세 수정

새 작업으로 바꾸기 전에 기존 CURRENT_TASK와 HANDOFF를 다음 위치에 함께 복사하여 보관한다. 해당 폴더는 첫 보관 시 만든다.

- `docs/collaboration/archive/<작업 ID>/CURRENT_TASK.md`
- `docs/collaboration/archive/<작업 ID>/HANDOFF.md`

진행 중인 작업의 요구사항을 바꾸면 작업 ID는 유지하고 명세 버전을 올린다. 변경 이유와 차이를 CURRENT_TASK 상태 기록에 남기며, 구현자는 사용한 명세 버전을 보고한다. 검토 의견과 이전 검증 근거는 삭제하지 않는다. 작업 간 관련성이 적거나 목표가 바뀌면 새 ID를 쓴다.

## 공유와 확인의 한계

- 커밋·push 전 로컬 변경은 웹 GPT가 GitHub에서 읽을 수 없다.
- 실제 DB·Windows 작업 스케줄러·로컬 로그는 Codex가 접근 가능한 환경에서 확인해 요약해야 한다.
- 로그와 환경 정보를 공유할 때 비밀값은 제거한다.
- GitHub에 접근할 수 없으면 그 사실과 미반영 내용을 알린다. 접근하지 못한 결과를 확인했다고 표현하지 않는다.
- 자동 감시·실행은 이번 구성에 포함되지 않는다. 양쪽에 작업 시작·검토를 요청하는 짧은 지시는 필요하다.
