# 이미지 한도 초과 분류와 통합 배치 보류

통합 배치는 확인된 해상도 한도 초과를 일반 이미지 오류와 구분하고, 같은 원본의 실패 기록을 반복 생성하지 않습니다. 이미지 제한·수집량·예약 시간·OCR 엔진·매칭 규칙은 그대로입니다. 원본 바이트는 다운로드 제한 안에서 메모리에만 두며 DB나 영구 파일에 저장하지 않습니다.

## 오류 코드

| 코드 | 발생 조건 | 통합 배치 처리 |
| --- | --- | --- |
| `OCR_IMAGE_LIMIT_EXCEEDED` / `PIXEL_LIMIT` | Sharp의 정확한 `Input image exceeds pixel limit` 예외 또는 메타데이터의 픽셀 수 초과 | 최초/변경 원본은 새 FAILED 시도, 저장 후 보류 |
| `OCR_IMAGE_LIMIT_EXCEEDED` / `DIMENSION_LIMIT` | 메타데이터의 가로 또는 세로가 20,000 초과 | 위와 동일 |
| `OCR_IMAGE_INVALID` | 지원하지 않는 형식·손상·디코딩 실패·다중 페이지 | 기존 실패/재시도 정책. 한도 초과로 추정하지 않음 |
| `OCR_IMAGE_TOO_LARGE` | Content-Length 또는 스트림 바이트 수가 용량 제한 초과 | 기존 용량 오류. 완전한 원본 해시가 없으므로 해시 보류를 새로 만들지 않음 |
| `OCR_IMAGE_HTTP_<상태>` / `OCR_IMAGE_REQUEST_FAILED` | HTTP 비성공 / 통신·시간 초과 | 이미지 검증 오류와 별개로 기존 실패/재시도 처리 |

기본 제한은 6,000,000바이트·12,000,000픽셀·가로/세로 20,000·다운로드 10초입니다. 기존 KOPIS `/upload/` 호스트 제한, 리디렉션 차단, 스트림 용량 검사와 HTTP 재시도 정책을 유지합니다. 픽셀 제한을 해제해 메타데이터를 다시 읽거나 전체 디코딩하지 않으며, 한도 초과 이미지를 축소·분할 처리하지 않습니다. Sharp가 메타데이터 단계에서 차단하면 가로/세로는 `null`일 수 있습니다.

## 상태 확립과 재확인

1. 기존 일반 재시도 대기와 처리 상한을 통과해 선택된 이미지를 기존 제한 안에서 다운로드합니다. 완전히 받은 원본에 SHA-256을 계산하고 같은 제한으로 검증합니다.
2. 한도 초과가 확인되면 `FAILED` 완료 시도에 새 오류 코드와 원본 해시를 기록합니다. 기존 RPC와 attempts의 nullable `content_sha256` 열을 그대로 사용하며, 성공 결과는 생성하지 않습니다.
3. FAILED 저장이 성공한 뒤 기존 `state-<프로젝트 hash>.json`의 `retries[ocr:<이미지 UUID>].image_limit`에 해시·URL·검증 조건 fingerprint·실패 시도 UUID·확인 시각·사유를 저장합니다. `until`은 다음 원본 확인 가능 시각입니다. 실패 저장이 실패하면 보류 상태는 확립하지 않고 DB 오류를 PARTIAL로 보고하여 기존 재시도로 남깁니다.
4. 기본 24시간 동안 해당 이미지를 다운로드/OCR/실패 기록 없이 건너뜁니다. 기존 `--recheck-hours` / PowerShell `-RecheckHours` 옵션을 재사용하며 새 환경변수는 없습니다.
5. 확인 시각 이후 선택되면 제한 안에서 원본을 다시 받아 해시를 비교합니다. URL·해시·검증 조건이 모두 같으면 Python OCR과 새 완료 시도를 생성하지 않고 다음 확인 시각만 갱신합니다. 이미지 검증/PNG 변환도 반복하지 않습니다.
6. 바이트가 달라지면 다시 검증합니다. 새 원본도 한도 초과면 새 FAILED 시도 한 건과 새 기준 해시로 보류를 유지합니다. 한도 내면 기존 성공 캐시 확인/OCR 경로로 복귀합니다. 손상 원본이면 일반 INVALID 정책으로 복귀합니다.

검증 조건 fingerprint에는 바이트·픽셀·가로/세로·다운로드 시간 제한, 검증 버전, OCR 파이프라인 버전, Sharp와 디코더 버전이 포함됩니다. URL 또는 fingerprint가 바뀌면 이전 보류를 적용하지 않고 다시 검증합니다. 한도 내 원본이 기존 성공 해시와 같으면 기존 캐시 복구 절차를 사용합니다.

보류 중 원본 확인 자체가 HTTP/통신/용량 오류로 실패하면 그 오류를 새 실패로 기록하고 PARTIAL을 유지합니다. 새 원본의 해시를 확정할 수 없으므로 마지막 확인된 보류와 기본 24시간 확인 간격을 유지하고 `last_check_error`에 별도 오류를 표시합니다. 작업 중단은 기존 보류를 없애지 않습니다.

### PF303360의 최초 상태

기존 이미지 `2896d808-7398-4a8a-a538-de3dd69f9988`의 `OCR_IMAGE_INVALID` 실패에는 해시가 없습니다. 과거 기록을 수정하거나 모든 INVALID를 한도 초과로 간주하지 않습니다. 다음 실행에서 기존 대기·선택 순서·상한에 따라 이 이미지가 선택될 때 한 번 다운로드/검증하고, 실제로 한도 초과라면 새 FAILED 시도와 로컬 보류 기준을 확립합니다. 따라서 최초 확립 실행은 새 실패에 따라 PARTIAL이 될 수 있습니다. 이전 읽기 전용 진단의 해시는 하드코딩하거나 운영 상태에 미리 쓰지 않습니다.

보류는 기존 로컬 체크포인트를 사용하는 통합 배치에 적용됩니다. 체크포인트를 삭제하거나 다른 PC에서 실행하면 URL·조건을 포함한 보류 기준이 없어 다시 확립해야 합니다. DB의 실패 해시만으로 당시 조건까지 같다고 추정하지 않습니다. 수동 `ocr:batch` 명령은 통합 배치 체크포인트를 읽지 않으므로, 반복 억제를 유지하려면 예약과 같은 `pipeline` 경로를 사용합니다.

## 집계와 검색 보호

`plan`과 `latest`의 최상위 `ocr_holds`는 전체 상태가 SUCCESS여도 표시됩니다.

- `count`, `items[]`: 현재 범위의 활성 상세 이미지 중 유효한 보류. 이미지 UUID·KOPIS ID·오류 코드·사유·해시·알려진 해상도·제한·실패 시도 UUID를 포함합니다.
- `checked_at`, `next_check_at`: KST 오프셋을 포함한 마지막 확인/다음 확인 가능 시각. 실제 실행 예약 시각을 뜻하지 않으며 처리 상한 때문에 더 늦게 확인할 수 있습니다.
- `status`: `WAITING_SOURCE_RECHECK` 또는 `SOURCE_RECHECK_DUE`.
- `last_check_error`: 보류 후 원본 확인에 발생한 별도 오류. 정상 해시 재확인 후 제거합니다.

통합 실행의 `stages.ocr` 집계는 다음과 같습니다.

| 필드 | 의미 |
| --- | --- |
| `new_limit_failures` | 최초 기준/변경 원본에서 새로 기록한 한도 초과 실패 |
| `held_unchanged` | 확인 시각 후 원본을 받아 같은 해시임을 확인한 보류 건수 |
| `held_skipped` | 확인 시각 전 보류 건수 + `held_unchanged`. `skipped`에도 포함 |
| `checked` | 원본 다운로드 확인 수. 동일 보류 원본 재확인도 기존 imageChecks 상한 소비 |
| `attempted`, `failed` | 동일 보류 건너뛰기는 증가시키지 않음. 실제 새 실패는 증가 |
| `succeeded`, `reused` | 동일 보류 건너뛰기는 증가시키지 않음 |

`plan.plan.ocr_held`도 보류 건수를 표시합니다. plan은 상태 갱신·다운로드·OCR·DB 쓰기를 수행하지 않습니다. 최초 기준이 없는 과거 INVALID의 실제 해상도는 plan만으로 확정할 수 없습니다. `latest`는 마지막 실행의 스냅샷이므로, 현재 시각 기준 대기/확인 가능 상태를 보려면 plan을 사용합니다.

보류를 성공 OCR이나 분석 완료로 간주하지 않습니다. 과거 FAILED·성공 결과·분석·수동 검토 행은 보존하고, 보류 자체는 이미지 비활성화나 공연 전체 검색 제외를 수행하지 않습니다. 다른 이미지의 결과와 확정 후보를 수정하지 않으며, 새 실패가 있으면 기존 PARTIAL 정책을 적용하고 나머지 대상 처리를 계속합니다.

## 적용과 검증

새 SQL 마이그레이션·환경변수·예약 재등록은 필요 없습니다. 기존 OCR 마이그레이션 `202610140002`와 통합 배치의 기존 필수 마이그레이션이 적용된 환경에 코드 변경을 반영하면 기존 예약이 새 코드를 읽습니다. 상태 파일을 초기화하지 마세요. 이번 변경에서 운영 마이그레이션·DB 변경·원본 HTTP 요청·실제 OCR·통합 배치는 실행하지 않습니다.

로컬 합성 이미지/HTTP 응답/가짜 OCR과 메모리 DB 테스트를 사용합니다. 검증 명령은 다음과 같습니다.

```powershell
node --input-type=module -e "await import('./server/easyOcrBatch.test.mjs'); await import('./server/concertPipeline.test.mjs')"
npm.cmd run test:collection
npm.cmd run test:easyocr
npm.cmd test
npm.cmd run build
./.venv/Scripts/python.exe -B -m unittest discover -s python/easyocr -p test_worker.py
```
