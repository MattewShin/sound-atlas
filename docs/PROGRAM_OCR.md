# 보관한 곡의 공연 검색과 프로그램 이미지 OCR

보관함·곡 상세에서 **이 곡의 공연 찾기**를 누르거나 공연 화면에서 기존 곡을 검색·선택한 뒤 지역·관람 기간을 설정합니다. 곡을 고르기 전에는 KOPIS 목록·상세·OCR을 요청하지 않습니다. 검색 버튼을 누르면 KOPIS 클래식 공연 목록을 가져오고, 상세 화면을 열기 전에 프로그램 자료를 확인합니다. `sty` 텍스트를 먼저 검사하고, 판단에 필요한 경우 `styurls` 이미지를 무료 [Tesseract.js](https://github.com/naptha/tesseract.js)와 Sharp로 읽습니다. 한국어·영어 모델을 함께 사용합니다. 유료 OCR·AI API, 정기 수집, 예약 실행은 사용하지 않습니다.

첫 검색은 최대 10개 후보를 2개씩 점진적으로 확인합니다. **더 찾아보기** 한 번으로 다음 최대 10개를 확인합니다. 처리 중에는 **중단**할 수 있습니다. 곡·지역·기간 변경이나 중단 후 늦게 도착한 응답은 현재 결과에 섞이지 않습니다. 곡 변경만으로 재검색하지 않으며 지역·기간 목록 캐시와 동일 공연의 OCR 캐시를 재사용합니다. 현재 직접 등록된 공연은 없으며, 곡 검색의 일치 결과는 확인된 KOPIS 프로그램에서 나옵니다.

주 결과에는 프로그램에서 대상 **작품 포함이 확인된** 공연만 나옵니다. 특정 악장을 선택했지만 프로그램이 작품 단위로만 쓰여 있으면 악장 연주를 확정하지 않습니다. 프로그램 이미지와 공연의 이름·날짜·장소가 일치해야 하며, 다른 시리즈 날짜나 번호, 연주자 경력 문구는 매칭 근거가 아닙니다. 작품번호·곡번호를 임의로 수정하지 않습니다. 후보는 8개 대표 상태로 집계합니다: 작품 포함 확인, 상세정보 조회 대기, 프로그램 분석 중, 이미지 OCR 필요, 추가 확인 필요, 프로그램 자료 없음, 분석 실패, 확인 범위 내 작품 불일치. **조회 시도**는 요청을 시작한 후보 수이고 **자료 처리 완료**는 자료 처리를 끝낸 후보 수입니다. 일부 후보·이미지만 읽었으면 전체 검색 완료나 확정 불일치로 표시하지 않습니다. 화면은 확인된 공연·확인이 더 필요한 공연·아직 확인하지 않은 후보의 세 그룹과 불일치 집계로 안내합니다. 최신 실제 검증과 한계는 [KOPIS 곡별 검색 v1.0](KOPIS_SEARCH_V1.md)을 참고하세요.

## 설치와 실행

Node.js 22.18 이상에서 프로젝트 루트 기준으로 실행합니다.

```sh
npm ci
npm run dev
```

`.env.example`을 `.env`로 복사하고 `KOPIS_SERVICE_KEY`에 발급받은 서버 전용 키를 넣습니다. 키는 브라우저 코드와 공개 `VITE_` 환경변수에 넣지 않습니다. 최초 OCR 때 Tesseract.js가 영어·한국어 언어 데이터를 내려받을 수 있어 네트워크 접근이 필요합니다. 사전에 내려받은 `eng.traineddata.gz`, `kor.traineddata.gz`를 서버에 배치했다면 `TESSERACT_LANG_PATH`를 그 디렉터리로 설정할 수 있습니다. 서비스키가 없어도 곡 평가·보관함·악장 상세는 볼 수 있습니다.

```sh
npm test
npm run build
npm run verify:ocr
npm run verify:ocr-cache
```

`verify:ocr`은 설정된 실제 KOPIS 키로 **PF302595만** 다시 조회하여 모든 소개 이미지, OCR 원문, 작품 연결, 다른 곡 검색의 캐시 재사용과 새 서버 객체의 디스크 캐시 재사용을 검사하는 수동 검증 명령입니다. KOPIS와 이미지 서버에 실제 요청을 보냅니다. `verify:ocr-cache`는 별도의 Node 프로세스에서 디스크 결과만 읽고 외부 API를 호출하지 않습니다. 결과 JSON은 Git에서 제외되는 `data/kopis-ocr-live.local/`에 남습니다. 출력에는 서비스키나 키가 포함된 URL을 넣지 않습니다. `npm test`는 외부 API를 호출하지 않는 자동 테스트입니다. 서비스키 없이 자동 테스트·빌드는 실행할 수 있습니다.

## 처리 제한과 저장

| 설정 | 기본값 | 용도 |
| --- | ---: | --- |
| `CONCERT_INITIAL_CHECK_LIMIT` | 10 | 첫 검색의 신규 후보 상한, 최대 10 |
| `CONCERT_MORE_CHECK_LIMIT` | 10 | 더 찾아보기 한 번의 신규 후보 상한, 최대 10 |
| `CONCERT_OCR_CACHE_TTL_MS` | 21,600,000 ms | OCR·분석 재검증 간격, 기본 6시간 |
| `CONCERT_OCR_CACHE_DIR` | `.cache/ocr` | OCR 원문·추출 결과·공연 분석 저장 위치 |
| `OCR_MAX_IMAGES_PER_CONCERT` | 8 | 공연별 이미지 처리 상한, 초과분은 미확인 |
| `OCR_MAX_IMAGE_BYTES` | 6,000,000 | 다운로드 이미지별 크기 상한 |
| `OCR_MAX_IMAGE_PIXELS` | 12,000,000 | 이미지 디코딩 화소 상한 |
| `OCR_DOWNLOAD_TIMEOUT_MS` | 10,000 ms | 이미지 다운로드 제한 시간 |
| `OCR_TIMEOUT_MS` | 35,000 ms | 이미지 1회 OCR 제한 시간 |

서버는 OCR worker 1개를 재사용하고 요청을 대기열에서 순서대로 처리합니다. 최초 언어 모델 준비 시간이 추가될 수 있습니다. 이미지의 원문·전처리 원문·출처·추출 작품·상태·처리 시각을 공연 ID와 이미지 URL별로 저장합니다. 캐시 유효기간이 끝나 재다운로드할 때 콘텐츠 해시가 같으면 OCR은 다시 실행하지 않습니다. 공연별 분석도 디스크에 저장하므로 같은 저장소를 사용하는 Node 재시작 후에는 재사용할 수 있습니다. `.cache/`는 Git과 정적 배포 결과에서 제외됩니다. 파일 쓰기가 불가능하거나 인스턴스 간 저장소가 공유되지 않는 배포에서는 메모리에서만 재사용되며, 재시작·다른 인스턴스 간 재사용을 보장할 수 없습니다. 영구 재사용이 필요하면 `CONCERT_OCR_CACHE_DIR`에 지속 볼륨을 연결해야 합니다. 디스크 파일 수는 현재 자동 정리하지 않으므로 운영 환경에서 용량을 관리해야 합니다. 정적 파일만 배포하는 환경은 Node API와 OCR을 실행할 수 없습니다.

한 공연의 다운로드·OCR 실패는 그 후보의 **자료 처리 실패**로 표시하고 다른 공연 검색은 계속합니다. 이미지가 일부만 읽혔거나 프로그램의 숫자·문맥이 흐릿하면 **추가 확인이 필요한 공연**으로 둡니다. 인물 소개와 이력 안의 곡명은 프로그램으로 사용하지 않습니다. 동일 공연의 이미지가 다른 곡 검색에도 필요하면 저장한 작품 목록으로 다시 비교합니다.

## 2026-10-12 실제 자료 검증

- `PF302595` 다니엘 델 피노 피아노 리사이틀: KOPIS 상세에는 `sty`가 비어 있고 소개 이미지 3개가 있습니다. 이미지 순서를 코드에 고정하지 않고 전부 읽었습니다. 공연 포스터에서 공연명·2026-10-17·클래시카 서울의 대응을 확인했습니다. 다른 이미지는 연주자 소개로 제외했습니다. 프로그램 구역의 **원본 OCR**에서 `F. Chopin`과 `Ballade No. 1in G minor, Op. 23`을 읽었습니다. 전처리 결과도 작품번호 23을 읽었고, 단어별 판독 결과와 프로그램 문맥을 검증하여 `chopin-ballade-op23-no1`에 연결했습니다. 첫 실제 OCR과 확인은 17,816 ms, 다른 곡으로 같은 공연을 비교할 때는 8 ms였고 추가 이미지 다운로드·KOPIS 호출은 각각 0회였습니다. 같은 캐시 디렉터리를 사용하는 새 서버 객체는 5 ms, 별도 Node 프로세스는 6 ms에 일치 결과를 읽었습니다. 언어 모델 파일은 첫 시간 측정 전에 이미 내려받아져 있었습니다. 이 시간은 한 로컬 실행의 측정치입니다.
- `PF300769` 큐리어스 피아노 스펙트럼 Ⅲ: 실제 소개 이미지 4개를 읽었고 공연명과 이미지의 시리즈 번호 충돌을 확인했습니다. 결과는 **추가 확인이 필요한 공연**이며 프로그램 작품 연결을 활성화하지 않았습니다. 이미지 속 `Prelude Op.3 No.2`만으로 현재 공연의 곡이라고 확정하지 않습니다.
- 자동 테스트는 숫자 23/28 불일치, 다른 줄의 높은 신뢰도 숫자 차용, 이력 문구, 다른 날짜·시리즈, 이미지 일부 처리, 동일 이미지의 곡별·재시작 재사용, 이미지 크기·시간 제한, 중단·중복 요청, 대표 상태 집계와 React DOM의 검색 진행을 확인합니다. 합성 자료 테스트는 위의 실제 이미지 검증과 구분합니다.

이미지의 화질·레이아웃과 OCR 오류 때문에 프로그램을 놓칠 수 있습니다. 읽지 못한 자료는 근거 없는 불일치로 바꾸지 않습니다. 실제 OCR을 확인한 실행 환경은 로컬 Node 서버입니다. Vercel용 함수·worker 파일 포함·임시 캐시 설정을 추가했지만 실제 Vercel 환경의 OCR worker, 언어 모델 다운로드와 모바일 실화면은 배포 후 검증해야 합니다. Vercel 임시 캐시는 인스턴스 간 공유되지 않으며 요청 실행 한도는 300초입니다. 배포 절차와 기존 KOPIS 목록·상세 API 검증 이력은 [KOPIS 설정 안내](KOPIS_SETUP.md)에 있습니다.
